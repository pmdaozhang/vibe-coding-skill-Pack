# Core Dev - 文档规范与版本管理

这个 skill 管理开发项目中 Superpowers 不覆盖的部分：
文档格式规范、版本管理纪律、迭代复盘流程。

工程流程（TDD、调试、验证、审查、Git 分支）由 Superpowers 负责。
本 skill 只管"文档怎么写"和"版本怎么管"。

## 文档分级规则

### A 级（完整文档流程）
新功能、架构变更、接口变更、数据模型变更
→ 必须建 features 文档 + test-cases 文档 + 更新 ROADMAP

### B 级（轻量文档）
Bug 修复、UI 微调、文案修改
→ 更新 CHANGELOG + 在相关 feature 文档追加变更记录

### C 级（仅 git commit 信息）
注释修改、格式化、重命名（不改行为）

## 需求文档格式（docs/features/）

每个功能一个文件，命名规则：编号-功能名.md（如 001-playback-speed.md）

结构：
- 标题行：功能名 + 编号 + 状态 + 版本号
- 需求描述：用户要什么，什么场景下使用
- 设计决策：为什么这样做，放弃了哪些备选方案
- 验收标准：可验证的条件列表（含异常场景）
- 变更记录：表格（日期/版本/变更/原因）
- 关联文件：实现文件路径 + 测试用例路径

## 测试用例格式（docs/test-cases/）

每个功能一个文件，命名与需求文档对应

结构：
- 标题行：名称 + 对应功能编号 + 版本 + 日期
- 正常场景：用例表格（用例/步骤/预期）
- 边界场景：用例表格
- 异常场景：用例表格
- 回归范围：改这个功能时不能坏的功能列表

## 版本管理纪律

### 开工前
- 读 docs/ROADMAP.md 确认任务属于哪个版本
- 新需求不在当前版本范围 → 问用户排到哪个版本

### 完成后
- 更新 docs/CHANGELOG.md（表格格式：类型标签 + 改动描述）
- 在 docs/ROADMAP.md 中打勾
- 类型标签：BUG / FEAT / REFACTOR / PERF / DOCS

### 发版时
- 更新 docs/RELEASE_NOTES.md（只写用户能感知的变化）
- 禁止写技术实现细节
- 打 git tag

### 代码与文档一致性
- 需求变更时：需求文档版本 +1 → 追加变更记录 → 同步改代码和测试
- 代码文件头部标注关联的功能编号
- 禁止只改代码不改文档
- 代码和文档必须在同一个 commit 里提交

## 迭代复盘流程

### 触发条件
用户说"复盘"、"回顾"、"总结一下"

### 执行步骤
1. 查看本次迭代的 git log（所有 commit）
2. 读 docs/CHANGELOG.md 本期变更
3. 读 docs/features/ 涉及的需求文档
4. 分析：这次做错了什么？哪条规则没能阻止？需要新增什么规则？
5. 提出规则修改建议给用户
6. 用户确认后修改 AGENTS.md 或 skill 文件

### 产出
- 更新后的 AGENTS.md 或 skill 文件
- 在 features/ 对应文档的变更记录里写入复盘结论
